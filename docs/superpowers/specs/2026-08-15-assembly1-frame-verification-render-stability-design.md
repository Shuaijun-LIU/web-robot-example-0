# Assembly1 Frame Verification Render Stability

## Goal

Prevent the Franka Assembly1 scene from disappearing while the Step 2 panel
shows `正在验证框架双侧接触`, without changing the trajectory, gripper closure,
contact verdicts, scene geometry, or any other robot scene.

## Evidence and root-cause hypothesis

- The rollback version can pass the frame-contact window in the local headless
  browser, but the frame has already translated about 6.7 mm by the eventual
  terminal diagnostic.
- The user-facing browser reproducibly loses the rendered workcell during this
  phase after rollback.
- The reverted patch changed only this phase and prevented the disappearance,
  but it rewrote joint velocities every physics step.
- The controller currently keeps driving all seven arm actuators toward the
  precomputed contact targets while the frame gripper is closed. The resulting
  contact load is sensitive to render/physics cadence and can destabilize the
  simulation on the user's browser.

The fix therefore removes the continuing position error at the phase boundary
without directly modifying generalized positions, velocities, objects, or the
contact solver.

## Considered approaches

1. **Fixed measured-pose hold (selected).** Capture each arm's seven measured
   joint positions exactly once when entering `frame-verification`; use that
   immutable snapshot as the joint actuator targets throughout the phase.
   Preserve the existing gripper target and verification state machine.
2. **Temporarily change actuator gains.** This could reduce contact force, but
   mutating MuJoCo model parameters at runtime has wider effects and requires
   exact restoration on every exit path.
3. **Fail the verification earlier.** This reduces exposure to unstable
   contact, but changes the task's verification semantics and may reject a
   contact that would settle within the existing window.

## Runtime design

`AssemblyStep2Controller` owns a frame-verification hold snapshot. On the
transition from `frame-clamp` to `frame-verification`, it reads the seven robot
joint positions for each arm and stores them once. While the phase remains
`frame-verification`, only the joint targets in the generated control frame are
replaced by this snapshot. Gripper targets remain exactly those generated by
the existing control-frame function.

The snapshot is cleared when Step 2 is reset, restarted, errors, or leaves the
frame-verification phase. Later Step 2 phases continue to use their existing
precomputed joint targets.

The implementation must never write `data.qpos`, `data.qvel`, task-object
poses, weld constraints, or proximity attachments.

## Failure behavior

Contact evidence, the 0.25-second uninterrupted contact window, the 2.5-second
verification timeout, and terminal failure reporting remain unchanged. If
verification fails, the existing failure-release path runs normally and the
Canvas remains mounted.

## Verification

- Unit test that the measured joint snapshot is a copy and remains fixed when
  source positions later change.
- Unit/controller contract test that frame verification uses the fixed snapshot
  while preserving gripper commands.
- Source contract test that the controller does not write `qpos` or `qvel`.
- Full unit test suite.
- Node 22 production Pages build.
- Browser run of Step 1 and Step 2 with phase observation, Canvas presence,
  scene status, console errors, and a post-verification screenshot.

## Scope exclusions

- No tuning of waypoints, gripper force, contact thresholds, object placement,
  or later Step 2 phases.
- No changes to Assembly2, SO101, XLeRobot, or shared scene geometry.
- No automatic attachment or scripted object motion.
