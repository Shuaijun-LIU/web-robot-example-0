## 2. 共用工作台和控制约定

场景独立键为 `frankaDemo3`、`frankaDemo4`；不改变 Demo1 默认入口。四台 Panda 分别能手动选中，自动动作运行时由任务控制器接管。

| 显示编号 / 内部编号 | 安装方位 | 根节点位置（m） | 底座偏航 |
|---|---|---|---|
| Arm 1 / r0 | 南 | `[0, -0.78, 0.10]` | 0° |
| Arm 2 / r1 | 东 | `[0.78, 0, 0.10]` | 90° |
| Arm 3 / r2 | 北 | `[0, 0.78, 0.10]` | 180° |
| Arm 4 / r3 | 西 | `[-0.78, 0, 0.10]` | −90° |

- Z 轴向上，底座安装面与桌面一致；编号不是观察者视角的左右顺序。
- 每臂 7 个关节控制量和 1 个夹爪控制量，共 32 个 actuator。夹爪命令 255 为打开、0 为关闭；命令不是实际夹爪宽度。
- HOME 关节角为 `[1.570796, -0.785398, 0, -2.356194, 0, 1.570796, 0.785398]` rad。
- 仿真步长 2 ms；`implicitfast`、elliptic friction cone、50 次迭代、10 次 no-slip 迭代。原生检查使用 MuJoCo 3.3.7，浏览器使用 WASM 3.3.8，因此分别验证。
- 指尖摩擦系数 1.0，夹爪 position stiffness 1000 N/m，actuator 力限幅 ±40 N。这是仿真配置，不代表对实机夹持力的标定。
- 播放器只写机器人 actuator controls；关节控制有 bias feedforward。没有物体吸附、运行中对象位姿重写、物体跟随约束或外加物体托举力。
- 人工选择控制对象时保留实际夹爪状态，避免切换到另一臂就把上一臂打开。

## 3. Demo3：产品检查、装箱与托盘出站

### 任务目的与分工

将两件待检商品逐一送到扫码器前，完成检查姿态后经中转位装盘，最后把装好的托盘推到出站区。

| 机械臂 | 职责 | 接触对象与交接条件 |
|---|---|---|
| Arm 1 | 从来料区抓商品、展示、放到中转位 | 商品由双指接触夹持；中转位确实承托后放开 |
| Arm 2 | 抓扫码器并对准商品检查面 | 扫码器实际夹持；检查后撤开，为中转腾出空间 |
| Arm 3 | 从中转位取商品并装盘 | 等 Arm 1 撤离后进入；商品落盘且有接触支撑再释放 |
| Arm 4 | 托盘出站 | 张开的双指推托盘外壁，托盘全程由连续支撑面承托 |

主要区域的名义 XY 中心：来料 `[-0.19,-0.34]`，扫码器 `[0.32,-0.16]`，中转 `[0,0.05]`，装盘 `[-0.28,0.25]`，出站 `[-0.40,-0.16]`。装盘到出站之间有连续支撑床，不靠悬空轨迹维持托盘高度。

动作依赖：

`Arm 2 取扫码器 → 对每个商品执行〔Arm 1 取/展示 → Arm 2 检查/撤开 → Arm 1 放中转/撤开 → Arm 3 取/装盘/撤开〕 → Arm 2 归还扫码器 → Arm 4 推盘出站 → 全部回 HOME`

共 66 个程序阶段，名义仿真时长 130.5 s。茶盒和咖啡盒尺寸不同，使用各自抓取高度，而非共用一个 TCP 抓取点。

### 资产与物理选择

全部来源于已有 benchmark：RoboTwin `024_scanner`、`112_tea-box`、`113_coffee-box`、`008_tray`，均为实例 0。源视觉网格、贴图、独立碰撞分块一并转换；应用源节点变换与 Y-up → Z-up 变换。

| 对象 | 当前质量（任务参数，非实测） | 说明 |
|---|---:|---|
| 扫码器 | 130 g | 复用源 functional point 1 作为光学头参考点 |
| 茶盒 | 90 g | 包围尺寸约 94.9 × 70.6 × 70.5 mm |
| 咖啡盒 | 100 g | 包围尺寸约 72.7 × 64.4 × 95.1 mm |
| 托盘 | 120 g | 出站动作是有支撑的推移，不是空中搬运 |

曾测试托盘边沿夹起和夹沿滑动：前者倾斜洒落，后者容易卡住边沿；所以采用外壁推移，没有添加隐形把手或固定约束。这一决策必须在后续复用时保留语义，不能把成功推盘标记成成功抓盘搬运。

### 成功定义与当前能力

- 检查使用几何条件：光学头沿轴距离 25–90 mm、离轴误差小于 20 mm、面对方向内积大于 0.9。
- **没有条码解码或图像识别**。后续若训练视觉检查，必须另建可见标签与识别监督，不能把对象名称当作模型识别结果。
- 最终两盒均在托盘目标范围内且与托盘有实际接触；托盘由出站位支撑；全部机械臂回 HOME。
- 目前是有依赖关系的四臂分工，不等于证明必须四臂才能完成。训练时应对比串行、双臂和四臂配置的质量与吞吐量。

## 4. Demo4：双臂托锅、另外双臂投放食材

### 任务目的与分工

Arms 1/3 抓住锅的两个把手并协同抬高，Arms 2/4 分别投放胡萝卜与番茄，然后共同把锅放回，松开并撤离。

| 机械臂 | 职责 | 主要动作 |
|---|---|---|
| Arm 1 | 南侧把手 | 部分打开进入把手环，重新对中，双侧接触闭合，托举和放回 |
| Arm 3 | 北侧把手 | 与 Arm 1 同步托举、保持、放回、退出把手环 |
| Arm 2 | 东侧胡萝卜 | 取料，经较高接近通道投放，向东清空后回 HOME |
| Arm 4 | 西侧番茄 | 取料，经西侧通道投放，待自然落稳后退出 |

动作依赖：

`双把手抓取验证 → 同步抬锅约 35 mm → 胡萝卜投放/稳定/撤开 → 番茄投放/稳定/撤开 → 双臂降低锅 → 锅底支撑确认 → 部分开爪/径向退出/抬高/全开 → 全部 HOME`

共 32 个阶段，名义时长 71.1 s。食材目前顺序通过共享开口，不是同时拥入锅口。托锅双臂在装料期间保持真实接触。

### 资产与碰撞腔体

- 锅使用 RoboCasa / Lightwheel `Pot054`，统一缩放至 65%，保留全部 38 个源凸碰撞分块。外包围尺寸约 257.5 × 178.4 × 107 mm。
- 胡萝卜、番茄使用 RoboCasa AIGen `carrot_0`、`tomato_0`，各保留源碰撞分块；备料盘复用 RoboTwin 托盘。
- 当前任务质量：锅 550 g，胡萝卜 55 g，番茄 70 g；质量、惯量属于仿真假设，不冒充实物测量。
- 锅不是封死的 convex hull。已有探针落入测试证明碰撞腔体开放，探针能落到内底。
- 支撑垫顶部 Z=0.116 m，锅初始 XML 原点 Z=0.118 m，自然落稳约 Z=0.117413 m；几何原点不是锅底接触面。

### 已解决问题与原因

1. 胡萝卜接近时曾擦到持锅腕部：高位进入通道向中心移动 18 mm，离开先向东移再回 HOME。最终路径原生/WASM 检查无非预期机器人接触穿透。
2. 食材刚进入锅内时尚未落稳：增加各 0.8 s 自然沉降阶段，未放宽速度判据，也未重写食材状态。
3. 放锅名义高度与真实承托高度有小差异：离线求解按 0.5 mm 增量有界下探，最多 2 mm；当前导出轨迹采用一次下探。承托后再开爪。
4. 手指全开后直接上提会挂住把手环：改为部分开爪、径向退出、上提、全开，沿原进入通道反向退出。
5. 放锅时接触点偶有单个采样瞬间消失：确认阶段最多原位等待 1 s，逐物理步检查原判据。超时仍失败，不把等待时间计入下一段动作，也不关闭碰撞检查。

待补的明确检查：独立的锅体世界竖直方向/倾斜角判据。名义路径已验证，但尚没有随机扰动恢复实验。

## 5. 可复用代码与程序接口

| 层 | 文件 | 职责 |
|---|---|---|
| 场景入口/分工 | `src/cooperativeWorkcells.js` | 场景键、HOME、角色、页面说明 |
| 程序定义 | `src/cooperativeMotion.js` / `.d.ts` | 程序合法性、阶段采样、成功判据 |
| 执行与物理检查 | `src/CooperativeMotionRuntime.js` | 写 actuator、逐步接触检查、阶段转换、失败原因 |
| UI 接入 | `src/CooperativeMotionController.tsx` | Play/Pause/Reset 与控制权 |
| 手动夹爪 | `src/CooperativeManualGripperController.tsx` | 切换目标时保留夹爪状态 |
| 视觉来源恢复 | `src/CooperativePresentation.tsx`、`src/cooperativeTextures.js` | 源纹理/UV，仅作用于新场景 |
| 资产与场景导出 | `scripts/build-cooperative-assets.py` | 统一变换视觉/碰撞，导出 MJCF 与 manifest |
| 离线动作求解 | `scripts/solve-cooperative-tasks.py`、`scripts/cooperative_pot_task.py` | IK、物理试跑与程序导出 |

程序文件 `public/assets/franka-cooperative/{scan,pot}-motion.json` 的语义：

```text
version = 1
scene = scan | pot
initialJoints = 7 维 HOME
initialObjects = [{name, position}]
phases = [{
  name, duration, optional settleTimeout,
  paths: 4 臂 × 多个 waypoint × 7 个关节角,
  grippers: 每臂 [阶段初值, 阶段末值],
  allowedContacts: 本阶段允许的 body-pair,
  carry: [{object, arm}],
  gates: 本阶段末需满足的物理条件
}]
```

阶段内使用 minimum-jerk 时间参数，关节 waypoint 间线性采样；这不是在线避障规划器。`allowedContacts` 是检查允许表，不是禁用其他碰撞。开局关节偏差大于 0.035 rad 或对象原点偏差大于 8 mm 会要求 Reset；不是“会自动适应任意初始条件”。

关键现行阈值：

| 检查 | 当前条件 | 后续 benchmark 注意点 |
|---|---|---|
| 抓取成立 | 双侧手指实际接触，开口 2–81 mm | 双侧接触不是所有负载下都稳固的充分条件，需继续检查滑移/承载 |
| 搬运中失抓 | 双侧接触连续丢失超过 0.12 s 则停 | 不能用物体到 TCP 的距离替代接触 |
| 非预期机器人穿透 | 超过 1 mm 则停 | 只覆盖与机器人有关的接触；还要补对象间碰撞和冲量审计 |
| 允许接触穿透 | 超过 2.5 mm 则停 | 这是数值容差，不是允许肉眼穿模 |
| 已支撑 | 真实接触且线速度低于 0.03 m/s | 增加持续时间和角速度，避免瞬时触碰被误判 |
| 容器内 | 容器坐标系位置范围、接触、速度低于 0.04 m/s | 当前取 body 原点；新任务应使用完整形状/体积包络，不只看中心 |
| 已释放 | 所有手指接触数为 0 | 还要观察撤离后是否稳固、不重新勾住 |
| 已回 HOME | 最大关节误差小于 0.025 rad | 任务完成与回位完成分开统计 |

## 7. 从现有演示转为训练任务

### 已能利用

- 有物体状态、机器人状态、实际接触和任务阶段，可作为自动标注与成功/失败事件的基础。
- 有可复用资产、合法动作程序、人工 IK 控制与逐阶段失败原因，可作为初始示范和数据采集起点。
- 已有原生/WASM 双引擎复验，可用于检测导出、控制时钟和数值差异。

### 必须新增，但尚未实现

1. `reset(seed, task_config)` 与可复现随机任务分布；所有采样保留碰撞和可达性约束。
2. 密集同步的 observation/action 记录：当前 motion JSON 是 waypoint 程序，报告是阶段汇总，**两者都不是完整训练 episode**。
3. 独立的策略输入与特权标注通道：真实对象位姿/接触可以监督或用于状态策略，不能偷偷给 RGB 策略。
4. 初始姿态、对象实例、角色分配、伙伴速度的受控变化；先小分布验证，再扩展，不要求一开始就跨所有任务泛化。
5. 新初始条件下重规划/人工补示范，真实执行验证；不能只平移最终对象坐标来“生成成功数据”。
6. 训练/验证/测试 seed、布局和源示范家族隔离；训练简单 BC，再考虑时序策略及多臂信息共享。
7. 新场景传感器规格与导出：旧 Assembly1 的全局/腕部相机不能视为已经接入 Demo3/4 的训练日志。
8. 标准环境适配层：可在原生 MuJoCo 中批量训练，Web 保留为观察、人工采样和回放入口；这是后续路线，不重新启用已放弃的旧 line3 工程。

完整数据字段、分布、基线和分阶段验收见[候选任务设计](benchmark-task-proposals-2026-10-07.md)。
